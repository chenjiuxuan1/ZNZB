# DS 通知配置与每小时看板可见性设计

## 目标

1. 六国“提前还款监控（每小时）”在看板页面始终可见，并明确区分“可执行”和“待发现”。
2. DS 调度监控复用 Metabase 定时巡检的视觉组件，保持连续单页结构。
3. DS 页面不展示项目码，只允许填写项目名称；项目码由服务端后台解析和保存。
4. DS 通知首次继承 Metabase 配置，随后允许独立保存、预览和发送测试。

## 看板与巡检

- 统一 inventory 同时返回已发现看板和来源看板。
- 来源看板即使尚未取得卡片也要显示为“待发现”，不能计入已巡检卡片。
- 定时巡检执行前继续调用现有内部 Metabase 发现流程；发现成功后自动合并为可执行看板。
- “提前还款监控”继续使用现有标题规则，与其他看板共用异常判断。
- 页面显示待发现原因，并说明需要 Metabase 登录态才能读取内部 dashboard。

## DS 项目配置

- 前端仅显示国家、项目名称和接入状态。
- 服务端保留 `projectCodes` 作为内部执行字段，但不通过页面要求用户输入。
- 保存项目名称时调用现有 n8n `resolve_project`；匹配成功后更新内部项目码。
- 匹配失败时保留同名项目之前已解析的项目码，并在对应国家卡片显示错误。
- 定时巡检只允许启用已经成功解析项目的国家。

## DS 通知配置

- 增加 DS 独立通知配置文件。
- 首次无 DS 配置时，以 Metabase 定时巡检通知配置作为默认值。
- 保存 DS 配置后，后续 DS 手动和定时扫描均使用 DS 配置，不影响 Metabase。
- 支持 KN Chat Bot 和 TV webhook，字段与 Metabase 巡检保持一致。
- 页面明确展示当前渠道、机器人或接收人、健康时是否通知。
- “预览消息”只生成 DS 测试文案，不发送。
- “发送测试”调用服务端通知能力，明确返回成功或失败，不触发 DS 扫描。

## 页面结构

连续单页，依次为：

1. DS 状态概览；
2. 六国项目配置；
3. 定时巡检配置；
4. 通知配置、消息预览和发送测试；
5. 最近结果与历史。

复用 `batch-hero`、`hero-stats`、`schedule-config-card`、`schedule-country-card`、`notice`、`sandbox-status` 等现有 Metabase 页面样式，不引入四标签导航和大图标指标卡。

## 部署

当前本地分支领先远端两个提交，因此截图中的服务器仍运行旧代码。完成本轮修改和测试后，需要将 `codex-show-scanned-dashboards` 推送到 GitHub，再由服务器 fetch/reset/restart。

## 验收

- 六国标签中的看板总数包含每小时看板。
- 每小时看板行可见，并显示“可执行”或“待发现”。
- 待发现看板不会被计入已检查卡片。
- DS 页面不存在项目码输入框。
- DS 页面可保存独立通知、预览消息、发送测试。
- DS 扫描结果可追溯实际使用的通知渠道和目标。
- 自动化测试、语法检查、浏览器桌面验收全部通过。
